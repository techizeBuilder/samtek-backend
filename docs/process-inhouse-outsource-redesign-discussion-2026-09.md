## QC placement under dynamic process steps (discussed 2026-09-22)

**The problem**: QC checkpoints were previously hardcoded to fixed positions in the old static step arrays — `productionMfgController.js`'s Child Part QC triggers off `procs[1]` (a literal array-index assumption baked on `['Fabrication','Assembly','Painting']`), and Machine's Final Testing QC triggers by searching for a step literally named `'Final Testing'` (`procs.findIndex(p => p.step === 'Final Testing')`). Neither survives dynamic, per-BOM process definitions — no step is guaranteed to exist at a given index or have a given name anymore. This was out of scope for Phase 1 (which never touched Production), surfaced once the user started thinking through Phase 2.

**What already exists and is reusable, confirmed by reading the code** (not rebuilding these):
- `QCJob`'s two-layer checklist (`ChecklistItemSchema`) — Production fills `actualValue`/`status` first (self-check), QC fills a separate `qcStatus`/`qcRemarks` verdict on the same rows. Already generic, not tied to any step position. Already how Sub Child Part, Child Part units, and Machine's Final Testing all work.
- `QCJob.source` already distinguishes flow shapes (`SubChildPartProduction`/`SubChildPartJobWork` — self-check skipped for the outsourced one; `ChildPartProduction` — `unitChecks[]`, independent per unit; `Production`/`Stock` for Machine — one final `checklist[]`).
- The Store-vs-Dispatch fork for Machine already exists — `ProductionOrder.saleId` is set or not at order creation; `saveFinalChecklist`/`submitDecision` already branch on it (`setSaleItemStatus` for a Sale-linked order, plain `Item.qty` increment otherwise). Nothing new needed here, just needs to be called from the right place.

**Decided design** (confirmed with the user 2026-09-22; corrected same day — see below):
1. A new per-step `qcRequired` flag on Process Definition (same place as `type`/`materialSource`/sequence) — for Child Part and Machine, R&D flags the ONE internal process step where the QC checkpoint sits, at BOM-definition time. **Not needed for Sub Child Part** — its rule is simply "always the last step," a fixed rule, not a per-BOM R&D choice, so no toggle shows there (same pattern as the materials picker already hiding itself for Sub Child Part).
2. **Correction (2026-09-22, same session)** — there is exactly ONE QC checkpoint per order, not "mandatory final gate plus optional extras." Original framing (final step always implicitly QC-gated regardless of the flag, on top of whatever R&D flags) was wrong and was explicitly corrected by the user: it would have forced R&D to define a SEPARATE "final" checklist in addition to whatever checklist covers the flagged step — extra scope in R&D's QC Parameters setup that doesn't exist today (today there's exactly one checklist per level: Sub Child Part's flat checklist, Child Part's initial+process combo, Machine's final checklist). Corrected rule: wherever R&D flags the one step, that IS the only QC check, reusing the single existing checklist structure for that level. If steps remain after the flagged step, Production simply finishes them with **no further QC review**, then the order completes straight to Store/Dispatch. If the flagged step happens to be the last step (as it always is for Sub Child Part, and as it usually was under the old hardcoded pipelines), behavior is unchanged from today.
3. Self-check-or-not follows step type at that one checkpoint, across all three levels (confirmed — "we are doing QC at a point anyway," so In-House vs Out Source only changes who checks first, never whether QC happens): an In-House checkpoint → Production self-checks, then QC department. An Out Source checkpoint → straight to QC department only, no self-check layer (mirrors Sub Child Part's existing Purchase-sourced behavior).
4. Multi-unit orders: confirmed — the one checkpoint needs independent per-unit tracking, for both Child Part and Machine. This generalizes Child Part's existing `unitChecks[]` pattern (already fully independent per unit) and moves Machine from its current hybrid (per-unit `processes[]`/`extraUnits[]` progress, but ONE shared `checklist[]` decided sequentially per unit) to the same fully-independent-per-unit model.
5. `QCJob` stays one-per-order (or one-per-unit, matching today's Child Part pattern) — no checkpoint-scoping needed now that there's only ever one checkpoint. What changes is only WHERE the trigger reads its position from (the flagged step) instead of a hardcoded index/name.
6. After the checkpoint's approval: if steps remain after it in the sequence, the order goes back to Production to continue them with no further QC — a genuinely new capability, since today reaching QC is always terminal from Production's side. If no steps remain, today's existing terminal logic runs unchanged (Store increment, or Machine's existing Sale-linked Dispatch-vs-Stock fork via `saleId`).

7. **Confirmed**: the system requires EXACTLY one step to be flagged `qcRequired` for Child Part/Machine (a Process Definition save is rejected with zero flagged, or with more than one). Reasoning: multiple flagged steps would imply a genuinely different checklist per checkpoint, which today's QC Parameters setup doesn't support (one checklist per level/item, not one per step) — that's a separate, bigger feature to consider only if the client actually asks for it later, not something to build speculatively. Since the flag is per-step in the schema either way, loosening this to "multiple allowed" later is additive, not a rework.

**Built (2026-09-22)**: only the `qcRequired` boolean field itself, per the scope decision above — `InternalProcessSchema.qcRequired` (`ProcessDefinitionSchema.js`), the exactly-one-flagged validation for Child Part/Machine only (`processDefinitionValidation.js`'s `requireExactlyOneQcStep` option, wired into `childPartBOMController.js`/`machineBOMController.js`; not into `subChildPartMasterController.js`), and a "QC Checkpoint" checkbox in `ProcessDefinitionEditor.jsx` that enforces the whole-definition exactly-one-flag behavior client-side (checking one step unchecks every other), hidden entirely for `bomLevel==='SubChildPart'`. No QCJob/Production/QC-controller changes — those stay Phase 2, as decided. **(Superseded 2026-09-23 — see "Stage 3b" below: the QCJob/Production/QC-controller wiring this flag was waiting on is now built.)**

**Scope decision**: this whole design is Phase 2 (Production/QC execution) work — none of the QCJob/Production changes above are being built now. The ONLY thing being built ahead of Phase 2 is the `qcRequired` flag itself on the Process Definition schema (Phase 1's BOM-side data model), so BOM Management doesn't need re-touching once Phase 2 starts. No QCJob restructuring, no checkpoint-scoped job creation, no Production resume-to-next-step logic yet.

## ProcessExecution.jsx UI fixes — duplicate Job Work card, category grouping, cross-unit fields (built 2026-09-23, before Stage 3b)

Found live while the user was testing a real Sub Child Part order right after Stage 2 shipped, screenshot-driven — three related bugs in `client/src/pages/production/ProcessExecution.jsx`, all in how the page renders a dynamic order's `processes[]`, none touching the backend:

1. **Duplicate/stale "Job Work" card.** A Sub Child Part order with a real dynamic `processes[]` (Stage 2) showed the OLD bespoke single-stage Job Work card (Assign Team/Start/QC Checklist, hardcoded to `orderKind:'SubChildPart'` regardless of shape) stacked on top of the NEW per-step cards, since both render conditions were independent and both matched at once. Fixed by deleting the whole bespoke block outright (per the user: *"you dont have to worry about lagacy as we are still devloping the project"*) — Sub Child Part orders now render through the same generic Process Steps engine as Child Part/Machine, no legacy branch. Removed alongside it: the now-orphaned state/handlers (`scpTeamChoice`, `scpChecklistDraft`, `scpTotalCost`, `scpBusy`, `handleAssignScpTeam`, `handleStartScpOrder`, `updateScpChecklistRow`, `handleSaveScpChecklist`, `handleSubmitScpToQC`) and the dead `'__scpJobWork__'` special case in `handleAssignTeam`. `subChildPartOrderMfgController.js`'s backend endpoints were left untouched (only the now-unused frontend calls into them were removed).
2. **No category grouping.** The per-step cards rendered as one flat list, with no visual grouping by the BOM Process Definition's Category label, for any order kind. Added `groupProcessesByCategory()` — partitions the flat `activeProcesses` array into consecutive runs sharing the same `proc.category`, rendering a heading per group. Purely presentational: each item keeps its real flat-array index (`{proc, idx}` pairs), so every existing action/lock (`canStart`, `handleSendForOutsourcing`, etc.) still operates on the ungrouped array untouched. A step with no category (an old hardcoded-pipeline order) gets no heading, same as before.
3. **Category/type lost on Unit 2+.** Only Unit 1 read straight off `order.processes` (the real BOM-built objects). Any later unit, before the backend had materialized it into `extraUnits[]`, was previewed by rebuilding from Unit 1's step **names only** via the OLD `buildStepsFromNames` helper — which stamps `type` from the legacy static `PROCESS_TYPE_MAP` (only knows old hardcoded names, not dynamic Process-Definition ones) and never set `category` at all. That's why category grouping and the type badge only ever showed on Unit 1 in the user's own screenshot. Fixed with a new `buildFreshUnitProcesses()` that copies Unit 1's real process objects wholesale (`category`/`type`/`materialSource`/`materialRefs`/`qcRequired`) and only resets the per-unit progress fields (status→Pending, team/dates/notes cleared), instead of rebuilding from bare names.

All three verified via `esbuild` syntax checks (no backend changes in this section).

## Stage 3b — built (2026-09-23)

The gap Stage 3 flagged as deferred ("nothing auto-creates the QCJob... judged too risky") — the `qcRequired` flag (Phase 1) staying inert, and cost/stock crediting never firing for a dynamically-named last step. Surfaced by a real bug report: a Machine order ending in `post painting` (not literally `'Final Testing'`) could run its whole pipeline and complete with **no cost captured and no stock credited**, since every existing cost/QC mechanism (`saveFinalChecklist`, `completeChildPartUnitPainting`, the old Sub Child Part submit-to-QC flow) was hardcoded to a literal step name or the old whole-order-status machine.

**Core addition**: `qcCheckpointIndex(order, procs)` (`productionMfgController.js`) — the ONE real QC checkpoint's position, from Phase 1's `qcRequired` flag (Child Part/Machine) or Sub Child Part's fixed always-last-step rule. Returns `-1` for any legacy order with nothing flagged (not Sub Child Part) — every existing hardcoded-name branch (Painting/Assembly/Final Testing refusals in `markProcessComplete`/`approveQC`/`rejectQC`) is gated to skip entirely when `-1`, so no live order's behavior changed.

Two independent positions, easy to conflate, kept explicit throughout: the **checkpoint** (`qcCheckpointIndex`, governs only who reviews) and **cost/expense** (always `procs.length - 1`, the true last step of the fully flattened sequence, independent of category boundaries or the checkpoint's own position — worked example: a `coating` checkpoint mid-Assembly, cost captured later on `post painting`, Painting's own last step).

- New `GET/PUT /orders/:id/qc-checkpoint(/submit)` (`submitQcCheckpoint`/`getQcCheckpoint`) — Production's self-check + submit for the checkpoint, generalizing `saveFinalChecklist`/`saveSubChildPartChecklist`/`saveChildPartUnitChecklist`'s Process stage into one endpoint. Dispatches by `orderKind`: Child Part reuses the staged `unitChecks[]` Initial/Process shape; Sub Child Part/Machine reuse the flat `checklist[]` shape (`ensureFlatChecklist`, already order-kind-generic, unchanged). Cost/expense required inline only when the checkpoint happens to coincide with the true last step.
- New `PUT /orders/:id/processes/:stepIndex/complete-final` (`completeFinalProcessStep`) — Child Part/Machine only (Sub Child Part's checkpoint is always last, never reaches this): completes the true last step when the checkpoint sat earlier, mirroring `completeChildPartUnitPainting` (Child Part) and a new `finalizeMachineOrderCompletion` helper extracted from `approveQC`'s own tail (Machine — lead-time sampling, Dispatch notification, linked-Sale status, safety-net QCJob creation, now shared between both call sites instead of duplicated).
- `qcController.js`'s `submitDecision` — the old `p.step === 'Final Testing'` completion block generalized to `qcCheckpointIndex(...) === procs.length-1`, and no longer excludes `SubChildPartProduction` (which now has a real dynamic `processes[]` pipeline, not the old bespoke single-stage flow) — one shared code path for "checkpoint is the last step," any kind. Sub Child Part's own block keeps only the genuinely kind-specific `Item.qty` credit.
- `decideChildPartUnit` — the hardcoded `procs[1]`/`'Assembly'` reopen-on-reject generalized to `qcCheckpointIndex`; a new Approve-side block flips the checkpoint step to `'Completed'` and unlocks the next step (mirrors `approveQC`'s auto-advance) when the checkpoint is mid-sequence, or credits `Item.qty` + applies pending cost (new `pendingProductionCost/Expense` fields on `UnitQCEntrySchema`, `QCJob.js`, mirroring `finalCheckProductionCost/Expense`'s existing pattern) when it's a newly-possible Child-Part-checkpoint-is-last-step shape.
- `outsourceWorkController.js`'s `receiveOutsourceHandoffRound` — now calls `ensureQCJobForOrder` and flips it straight to `'Pending'` (no self-check layer for an Out Source checkpoint) when the received step is `qcRequired`, closing exactly the gap Stage 3's own comment flagged.
- `approveQC`/`rejectQC` — refuse the checkpoint index the same way they already refused `'Final Testing'`, so Production can never self-certify past the real QC department's own decision.
- Frontend: new `QcCheckpointPanel.jsx` (generalizes `FinalChecklistPanel.jsx` + Child Part's inline staged UI, reusing the same `ChecklistStepper`), mounted on whichever card matches a client-side mirror of `qcCheckpointIndex`. A new "Complete & Enter Cost" dialog/button (`handleCompleteFinalStep`, mirrors `handleCompletePainting`) for the true-last-step-after-an-earlier-checkpoint case. Existing Mark Complete/Approve/Reject buttons hidden for the checkpoint index, same pattern Final Testing already used.

All touched files verified via `node --check`, import tests, and `esbuild` syntax checks. Not yet done: `/qc/jobs`' own review components weren't touched (they already render off `job.checklist`/`job.unitChecks` shape, not step name, so should need no change — worth a live click-through, not yet done) and category-grouping headers for the checkpoint/final-step cards weren't specially highlighted (they render in the correct category group like any other step).

## First-step outsource material send — testing bridge (discussed + built 2026-09-23)

**The problem, hit while testing Stage 3b end-to-end**: `/accounts/purchases/sub-child-job-work` (Outsource Work) throws an error whenever Purchase tries to send the very first hand-off of a Child Part / Machine / hybrid-Sub-Child-Part order whose first process step is Out Source. This is the exact, deliberate gap from Stage 3's own scope cut — `outsourceWorkController.js`'s `sendOutsourceHandoffRound` throws `HttpError(501, ...)` whenever `handoff.isFirstStepOfOrder && handoff.rounds.length === 0`, because that's the one case that would need a real Store pull, and porting `SubChildPartJobWorkOrder`'s proven cut/whole/leftover logic under time pressure risked a real inventory bug (see Stage 3's own write-up above). A **pure** Out Source Sub Child Part order never hits this — it still auto-routes straight to the old, fully-working `SubChildPartJobWorkOrder` flow untouched; this gap is specifically the new hand-off model's first-step case for the other two/three shapes.

**Why this needs solving now, not later**: the real fix (an actual Store deduction, generalized from `SubChildPartJobWorkOrder`'s proven per-material cut/whole-sheet/catalog/leftover mechanic to `materialRefs`-driven Child Part/Machine BOM lines) depends on the Logistics/vendor-selection handshake (Purchase → Logistics → Store/Production, see the section below), which is explicitly deferred and not being built yet. Without *some* working path here, Stage 3b's whole QC-checkpoint flow can't be exercised end-to-end for any order whose pipeline happens to start with an Out Source step. So the decision is to build a **temporary testing bridge**, not the real thing — clearly distinguished in code so it's never mistaken for finished, and swapped out wholesale once the real Logistics/vendor build happens.

**Decided design (confirmed with the user 2026-09-23)**:

1. **Material determination still runs for real and is shown to Purchase** — this part is NOT stubbed. Reuses the exact same proven logic, not a rebuild:
   - For a Sub Child Part order (its own single `sourceItem` raw material line): the same cut-piece vs whole-sheet choice, catalog vs leftover `dimensionVariants[]` resolution, and quantity math `SubChildPartJobWorkOrder`'s existing send flow already has (`subChildPartJobWorkOrderController.js`) — this is the same "material-options" resolution the OLD Purchase dialog already calls (`/api/purchase/sub-child-job-work/:id/material-options`), which is untouched and stays untouched.
   - For a Child Part/Machine order (its first internal process's `materialRefs`, which can point at more than one BOM material line, per Phase 1's materials picker — `ExplicitMaterials` only, since nothing's been assembled yet to reference as `AssembledPart`): the SAME sheet-metal-group / length-fabrication-group / plain-material resolution the regular Material List already uses (`bomMaterialGroupsService.js`'s `sheetMetalGroupsFromBOM`/`plainMaterialGroupsFromBOM`/`lengthFabricationGroupsFromBOM`, `SheetMetalPlan`-driven area calc) — per the discussion doc's own §6 principle ("no new quantity-calculation logic is introduced"), just applied per-`materialRefs`-line instead of the single fixed line Sub Child Part has. Purchase sees the real "this order needs X of material Y, here are the available catalog sizes / leftover pieces" picture for every referenced material line, not a placeholder.
2. **Selecting a specific material option is OPTIONAL, not required, to send.** Purchase can click Send without picking a cut/whole choice or a catalog/leftover variant at all — the information is shown for reference (so testing looks and feels like the real flow), but nothing forces a selection before the round can go out. Confirmed with the user explicitly: *"it should show but user can proceed without selecting the material."*
3. **Real Store inventory is never touched by this path**, regardless of whether Purchase makes a selection or not. If a selection IS made, it gets recorded on the round (same field shape as `SubChildPartJobWorkOrder`'s `rawMaterial`/round records) purely for reference/record-keeping — never applied as an actual `Item.qty`/`dimensionVariants[].subStock` deduction. This is the actual "dummy" part of the bridge.
4. **Cost/expense capture at Receive stays exactly as it already works — fully required, unchanged.** Initial read of "no bills" was a misunderstanding on my part, corrected by the user: *"i think the bills i meant is when we will have vendor system we need vendor bills right, so as of now its another thing and does not affect anything here, so the cost upload needs to be present."* "Bills" refers to a future formal vendor-invoice/billing system tied to Vendor Master (not built, not part of this bridge, not part of this phase at all) — the existing job-work cost total field (mirroring `SubChildPartJobWorkOrder`'s `totalJobWorkCost`, captured once at final receive) is a separate, already-working mechanic and is NOT waived by this change.
5. **Scope: all three order kinds that can reach this gap** — Child Part, Machine, and hybrid Sub Child Part — confirmed explicitly (*"yes all three"*). A pure Out Source Sub Child Part order is unaffected either way, since it never reaches this code path at all.

**Built (2026-09-23)**:

- `ProductionOrder.js`'s `OutsourceHandoffSchema.rawMaterial` gets one new field, `dummy: Boolean` — the visible marker this section called for. Set `true` whenever `sendOutsourceHandoffRound` handles a first-step-of-order send this way, so a future pass wiring up the real Logistics/vendor handshake can tell a dummy send apart from a real one at a glance.
- `outsourceWorkController.js`'s new `getHandoffMaterialInfo` (`GET /api/outsource-work/orders/:id/handoffs/:handoffId/material-info`) — returns `{kind:'none'}` for any hand-off that isn't a still-unsent first step. For Sub Child Part, reuses `computeSubChildPartRawMaterialAvailabilityLive` plus the exact same catalog/leftover resolution `subChildPartJobWorkOrderController.js`'s `getSubChildPartJobWorkMaterialOptions` already has — `resolveCatalogVariant`/`wholeSheetTargets` exported from that file rather than duplicated, so this is a genuine reuse, not a rebuild. For Child Part/Machine, a simpler per-`materialRefs`-line lookup straight against the BOM's own `materials[]` (needed qty = per-unit qty × `orderQuantity`, available qty from the matching `Item`) — no cut/whole/catalog/leftover picker for this shape, since `materialRefs` can span several different material lines/types and building that full picker is a bigger lift than this bridge calls for (selection is optional either way, and nothing gets applied to real stock regardless).
- `sendOutsourceHandoffRound` no longer throws the 501 for a first-step send. `req.body.materialSelection` (`materialCase`/`dimensionVariantId`/`leftoverVariantId`/`notes`) is read if present and written onto `handoff.rawMaterial` purely for reference, alongside `dummy: true` — no `Item`/`dimensionVariants[]` mutation happens in this code path at all, selection present or not. The round then pushes exactly the same way every other hand-off's round already does.
- Frontend (`SubChildJobWork.jsx`): the handoff Send dialog's old "sending it isn't wired up yet, this will show an error" warning is gone. For a still-unsent first step, it now fetches and shows `getHandoffMaterialInfo`'s result — a small material table for Child Part/Machine's `multi` shape, or, for Sub Child Part's `plain`/`sheet`/`length` shapes, **the exact same picker UI** the old `SubChildPartJobWorkOrder` dialog has always had (confirmed with the user from a screenshot: *"i want same old ui"* — Send Cut Piece/Send Whole Sheet toggle, catalog-stock radio, leftover radio cards with the "matches a whole sheet size"/"does not match this plan's sheet size" annotations, the "Sends N whole sheet(s) of L×W×T" summary line, the tight-margin warning, everything). Rather than duplicate that ~150-line block, it's now a shared module-level function, `renderMaterialPicker(opts)`, taking the picker's state as plain props — both dialogs call it, the old one unchanged in behavior, the new one bound to its own parallel state (`handoffMaterialCase`/`handoffSourceVariantId`/`handoffStockPiecesConsumed`/`handoffCombineLeftover`/`handoffImm*`, plus `handoffCutMarginInfo`/`handoffLengthCombineLeftover` mirroring the old dialog's own derived values). Picking anything in it is still entirely optional — the Send button is only ever gated on at least one step being checked. An explicit amber note under the picker says no real stock moves yet.
- Cost/expense at Receive is completely untouched by this change, exactly as decided — `receiveOutsourceHandoffRound` still requires nothing extra here (the round's own `costTotal`/QC-checkpoint wiring from Stage 3b already governs that, unrelated to this material-send gap).

All touched files verified via `node --check` and import tests (backend) and `esbuild` (frontend).

## In-House material consumption gap — per-step material picker (discussed + built 2026-09-23)

**The problem, found while the user was testing Stage 3b live**: the old hardcoded pipelines had an implicit, unwritten rule — material consumption was always tied to whichever step came first (`'Job Work'` for Machine, `'Assembly'` for a MachineBOM-driven order), so `assignTeam`/`startProcess` (`productionMfgController.js`) could hardcode their "material must be issued before you can assign a team, a team must be assigned before you can start" gate to that one literal step name. A dynamic Process Definition order's first step is whatever R&D typed into the catalog — it essentially never matches `'Job Work'`/`'Assembly'` literally, so both gates silently never fire. Traced further: it's not just that the check is name-hardcoded, there is currently nowhere for it to even point. `ProcessDefinitionSchema.js`'s own comment says `materialRefs`/`materialSource` are **"only meaningful when type === 'OutSource'"** — built purely to resolve what to hand Purchase for an outsource hand-off. An **In-House** internal process has no material association in the schema at all today, and `ProcessDefinitionEditor.jsx`'s whole materials-picker block is gated on `proc.type === 'OutSource' && bomLevel !== 'SubChildPart'` — nothing renders for In-House, ever. Net effect, confirmed by the user: *"because of this gap i can start a work without issuing material."* Sub Child Part is unaffected either way — one raw material, one consumption point, no ambiguity possible; this gap is Child Part/Machine only.

**Decided design** (confirmed with the user 2026-09-23, several rounds — this section captures the full result, not just the conclusion, since design intent matters here as much as the mechanics):

1. **Generalize the existing Out-Source-only materials picker to every internal process, In-House included.** Same `ProcessDefinitionEditor.jsx` picker, same `materialRefs`/`materialSource` fields on `InternalProcessSchema` — just drop the `type === 'OutSource'` restriction. The literal first internal process overall keeps its existing forced rule (always `ExplicitMaterials`, a pick required) — that rule was never type-specific in spirit, it was just only reachable through the Out-Source branch before.
2. **`assignTeam`/`startProcess` generalize off the step's own `materialRefs`/`materialSource` instead of a literal step name** — same pattern already used for `qcCheckpointIndex` in Stage 3b (position/data-driven, not name-hardcoded). Empty `materialRefs` (or `materialSource:'AssembledPart'` with nothing additionally picked) → no material gate, works on the prior step's output. Non-empty `materialRefs` → those specific referenced lines must show `Issued` on the order's own material demand ledger before a team can be assigned or the step started — reusing `getUnissuedMaterials`'s existing `filterGroups` parameter (already used once, by `getPartUnissuedMaterials`, to scope the exact same check to one Sub Child Part's own lines) rather than building new plumbing.
3. **Assembled-part and explicit-material picks stop being mutually exclusive.** Today, switching a step to `'AssembledPart'` clears `materialRefs` to `[]` — the two are a single XOR radio. Confirmed with the user this is wrong: a step can legitimately need *both* — the assembled sub-build **and** an additional fresh material/tool on top of it (e.g. a bracket fastened onto an already-assembled frame). `materialRefs` stops being cleared on switching to `AssembledPart`; the assembly-reference pick (item 4 below) and the materials/tools pick become two independent, simultaneously-available pieces of the same step, not one radio choice.
4. **Assembly-reference consumption (Child Part's `subChildParts[]`, Machine's `childParts[]`) is explicit and one-time per line, not inferred from category position.** The original worry was a strict "once Assembled Part appears, no later step can be Not-Yet-Assembled" rule breaking the already-documented case of two independent categories each building something separate that only merges at a later one (a flat sequence has no concept of separate "lineages," so a blanket monotonic rule would wrongly block that). The user's resolution, confirmed as the right one: don't infer anything from position at all. Each step's `AssembledPart` choice gets its own explicit pick from the BOM's assembly-reference lines (a genuinely different list from the materials/tools list — same `materialRefs` field underneath, same chip-picker UI already distinguishes them by color) — R&D marks exactly which specific Sub Child Part/Child Part reference is being folded in **at this step**. Once a reference line appears in *any* step's pick, it's consumed — removed from the pickable pool for every step after it, computed live by walking the definition in its current order (no new stored state, so reordering/deleting steps during editing can't leave anything stale). An `AssembledPart` step with nothing left to consume just shows an empty pick list — meaning "nothing new folded in here, this step continues on what's already built," a normal and common case (e.g. a coating step right after an assemble step). Two independent chains now just each pick their own distinct references at their own assembly point — nothing conflicts as long as no reference gets picked twice, which the pool-depletion rule already prevents structurally.
   - **Validation question, confirmed 2026-09-23**: yes, enforce it — saving is rejected if any assembly-reference line is never consumed, or if two steps both claim the same one, mirroring the existing exactly-one-QC-checkpoint check.
5. **A raw material/tool line's BOM quantity can be split across more than one step referencing it**, worked example from the user: a BOM line of 4 nut-bolts, 2 consumed at one step and the remaining 2 at a later step. This needs `materialRefs` to carry a quantity per reference where it's actually split, not just a bare id — but only when it's actually split. While a line is picked by exactly one step, nothing changes from today (implicit full BOM quantity, no extra field shown). The moment a second step also picks that same line, both steps' pickers show a quantity input, live-validated so the running total across every step referencing that line can never exceed the BOM's own quantity for it — an allocation of an already-computed number, never a new calculation, keeping faith with the "reference only" principle in "Confirmed design decisions" item 6 above.

**What stays exactly as it is, confirmed not touched by any of this**: Sub Child Part's own picker (still hidden entirely — one raw material, one consumption point, no picker needed at that level). The Out-Source hand-off material-resolution logic (Stage 3, the testing bridge above) — unaffected; it already reads `materialRefs` off whichever step is flagged, generalizing the picker to In-House doesn't change what an Out-Source step's own hand-off does with its own refs. The `qcRequired`/QC-checkpoint mechanism (Stage 3b) — fully independent of this, no interaction.

## Multi-unit outsource handoff batching (discussed + built 2026-09-25)

**Found live testing a real Child Part order** (`CP-001`, "Fan", 2 units) through Stage 3b and the material-picker work — two things surfaced together, one a real bug, one not:

1. **Purchase's Outsource Work list "Qty" column is actively wrong for Child Part/Machine rows**, not just unclear — worse than first assumed. `outsourceWorkController.js`'s `normalizeHandoffRow` (Child Part/Machine) and `normalizeJobWorkOrderRow` (Sub Child Part) both set the same field, `orderQuantity: order.orderQuantity` — the WHOLE order's build quantity. For Sub Child Part this is a defensible number (one raw material, one consumption point — order qty effectively IS the quantity signal). For Child Part/Machine it's wrong: `OutsourceHandoffSchema.unitIndex` is a single number, confirmed by reading `requestOutsourceHandoff` — one handoff always covers exactly ONE unit, no batching exists today. So a handoff covering Unit 1 alone still displays "Qty: 2" (the order's full count), even though this specific handoff only concerns 1 of the 2 units.
2. **Non-bug, confirmed with the user.** A step card showing no material table for `grinding`/`coating` (In-House, downstream of an Out Source `welding` step) traced to `buildOrderStepsFromProcessDefinition` snapshotting the Process Definition once, at order-creation time (`childPartReorderService.js` line 623 — a fresh `ChildPartBOM.findOne(...)` at that moment, confirmed correct). This test order was created BEFORE those two steps' material picks were added to the Process Definition — an already-created order never retroactively follows a later edit to its BOM's master template, same snapshot principle as "locked BOMs cannot be modified by Production" elsewhere in this system. Confirmed by the user (*"yes it is old order before we created the process dynamic thing"*) — no fix needed.
   - Separate, real, still-open bug found in the same pass, unrelated to either of the above: `resolveStepMaterialLines`'s `perUnitNeed` always reads a BOM line's full `l.quantity`, never `proc.materialQuantities` — for a line split across two steps (the 4-nut-bolts, 2+2 case from the material-picker work), once its table renders for both steps, each will show the line's FULL BOM quantity, not its own split share. Not yet fixed — tracked here for whenever this area is next touched, not part of the batching work below.

**The real gap (item 1) — design discussion, 2026-09-25**:

User's own scenario: a multi-unit Child Part order whose pipeline starts with an Out Source step — Production may send every unit for that first hand-off together, since none has done any in-house work yet. Later, a SECOND Out Source step further down the pipeline is reached at different times per unit — Production may hold Unit 1 there and keep working Unit 2 through the same in-house steps until it also arrives, THEN send both together. Neither case is representable today — `unitIndex` only ever covers one unit, so batching is impossible; each unit needs its own separate handoff, and Purchase's list shows each as if it needed the FULL order quantity (item 1 above), compounding the confusion rather than resolving it.

**Confirmed design decisions (2026-09-25)**:

1. `OutsourceHandoffSchema.unitIndex: Number` → `unitIndices: [Number]` — a handoff covers a fixed SET of units, decided once at creation, not a single unit. Existing handoffs read as a one-element array, same legacy-shape convention used throughout this project.
2. **Same step INDEX required to batch** (confirmed, not just same step name) — units must be at the literal same position in their own `processes[]`/`extraUnits[].processes` to be combined into one handoff. A unit that diverged via rework could have a different index for what's nominally "the same" step name — deliberately not handled; name-matching across diverged units is out of scope.
3. **A handoff is atomic once created — no partial completion inside one.** Send 3 of 5 units in one handoff → all 3 come back together as one Sent→Received round; there is no partial-within-the-3 state. The other 2 units, not included, simply aren't sent yet — whenever Production does send them, that's an entirely NEW handoff, created through the same flow, batched however Production chooses at that point (together, or split into two singles). Confirmed by the user's own framing (*"if we send 3 of 5 unit in first go then we will receive the 3 unit at one, and later those 2 unit will send by same logic if the production send them both or one at a time"*) — this keeps `OutsourceHandoffRoundSchema` completely unchanged; the receive-side work is just "iterate `unitIndices`, advance each unit's own `processes[]`/QC the same way the current single-unit path already does it once, N times instead of once."
4. **New capability needed, not yet built**: given a unit + step, find every OTHER unit whose own next actionable step sits at the same index and is still `outsourceStatus: 'NotStarted'` — the data behind a new "who else is on this step" picker Production sees when clicking "Send for Outsourcing," replacing today's implicit single-current-unit send.
5. **Qty in the Purchase list, once this is built**: for a Child Part/Machine handoff row, show `unitIndices.length` (how many units THIS handoff covers) instead of `order.orderQuantity` — what the user actually wants (*"means how many part of fan not the material"*), and something the schema can finally answer accurately per row.

**Built (2026-09-25)**:

- `ProductionOrder.js` — `OutsourceHandoffSchema.unitIndex: Number` → `unitIndices: { type: [Number], required: true }`, per item 1. `isFirstStepOfOrder`'s own comment corrected to reflect it's a step-position property, not tied to a specific unit.
- `outsourceWorkController.js`:
  - New `getEligibleUnitsForRun(order, referenceUnitIndex, stepIndices)` — walks every unit of the order (skipping any not yet materialized in Process Execution, same boundary `resolveUnitProcesses` already enforces), checking each against `validateContiguousOutSourceRun` (unchanged, reused as-is). One addition beyond item 2's own wording: a candidate unit must also carry the exact same step NAME as the reference unit at every index in the run, not just pass validation independently — same-index batching alone doesn't fully rule out a diverged unit (rework) having a *different* step sitting at that same numeric position; this closes that gap cheaply rather than leaving it as a known risk. New `GET /api/outsource-work/orders/:id/eligible-units?stepIndices=..&unitIndex=..` (`getEligibleUnits`) exposes this to the frontend picker.
  - `requestOutsourceHandoff` — request body is now `{ unitIndices: [Number], stepIndices: [Number] }`. Every included unit is independently validated against the shared `stepIndices`, with the same step-name-consistency check as above (any mismatch fails the whole request, naming the offending unit). `isFirstStepOfOrder` simplified to `sorted[0] === 0` (item 1's consequence — no longer tied to whether unit 0 specifically is in the batch).
  - `sendOutsourceHandoffRound`/`receiveOutsourceHandoffRound` — both now loop `handoff.unitIndices`, applying the exact same per-unit status-stamp logic each already had for its one unit, to every included unit. `OutsourceHandoffRoundSchema` itself untouched, per item 3 — a round still has no per-unit state. `ensureQCJobForOrder` still called once after the receive loop, not per unit — confirmed order-scoped before making this change, not per-unit.
  - `getHandoffMaterialInfo`'s Child Part/Machine branch — `buildQty` now reads `handoff.unitIndices.length` instead of `order.orderQuantity`, fixing the same order-qty-vs-handoff-scope bug the Purchase list's Qty column had, at this second call site.
  - `normalizeHandoffRow`/`normalizeJobWorkOrderRow` — both add `unitCount` (item 5): `handoff.unitIndices.length` for a Child Part/Machine row, `orderQuantity` unchanged for a Sub Child Part row (no per-hand-off subset there). `orderQuantity` itself stays on both rows, just no longer what the Qty column reads.

## Sub Child Part Start blocked by a Machine-only gate — found + fixed (2026-09-24)

Found during the user's first live click-through of a Sub Child Part order's dynamic `processes[]` (a Fan Bush/SCP-002 order, `cutting` In-House → `drilling` Outsourcing): clicking Start on `cutting` failed with "Cannot start process: BOM has not been verified by R&D yet." — a Machine-only R&D approval concept that has no equivalent at either Sub Child Part or Child Part tier.

**Root cause**, `productionMfgController.js`'s `startProcess`: a single variable, `const isSCP = order.orderKind === 'ChildPart'`, was reused for five different checks across the function. The name says "is Sub Child Part" but the value checks the MIDDLE tier (`'ChildPart'`) — almost certainly a leftover from before this project's Sub Child Part/Child Part terminology swap (see "Terminology / gotchas" below) fully propagated through this file. `order.bomVerified`/`order.materialIssued` are flipped exclusively by `processRDRequest`'s Initial BOM approval against `RDBOM`/`MachineBOM` (confirmed against `bom-hierarchy-redesign-build-2026-09.md` §20) — genuinely Machine-only, never set for either lower tier. Net effect: Child Part orders skipped the gate correctly (by coincidence of the string match), Machine orders were correctly gated, but a real Sub Child Part order fell into the gated branch and was permanently blocked, since those two flags default `false` and nothing ever sets them for that kind.

**Fix**: split the overloaded variable into two correctly-scoped ones. `isMachine` (`orderKind === 'Machine'`) now gates the R&D bomVerified/materialIssued check and the two other checks in this function that are genuinely Machine-only (the legacy `Job Work` step, and the MachineBOM-pipeline `Assembly` branch) — both previously also riding on the same broken `!isSCP` proxy, working only by coincidence since a dynamic Sub Child Part step is unlikely to literally be named `Job Work`/`Fabrication`. `isChildPart` (renamed from the same misleading `isSCP`) kept for the one check that's genuinely Child-Part-specific — the per-unit Painting/QC gate at idx 2, which queries `QCJob.findOne({source:'ChildPartProduction', ...})` and would have been wrong to broaden to Sub Child Part too.

## Out Source checkpoint self-check — design reversed (2026-09-24, same day)

**Found on the very next live click-through**, same Fan Bush/SCP-002 order: after the previous fix, Production could reach `drilling`'s checkpoint, but sending it for outsourcing and receiving it back left cost/expense uncapturable and no QCJob ever appeared in `/qc/jobs`. Root cause was two compounding bugs, not one:

1. `receiveOutsourceHandoffRound` decided QC-Pending vs. Completed off `proc.qcRequired` — a flag Sub Child Part orders never set (its checkpoint rule is fixed-last-step, not a flagged one; the BOM editor doesn't even show the toggle at that tier). So the checkpoint silently completed with no QCJob ever created.
2. `QcCheckpointPanel` had no `proc.type` gating and showed an editable self-check UI (Production Cost/Expense fields, Pass/Fail checklist) the moment `proc.status === 'In Progress'` — which, traced further, happened the instant the PRIOR step completed (`markProcessComplete`'s auto-advance-next-step-to-In-Progress logic fires for ANY next step, blindly, regardless of type) — well before the outsource hand-off had even been sent, let alone received.

**Original design reversed, confirmed with the user 2026-09-24**: Stage 3b's "An Out Source checkpoint → straight to QC department only, no self-check layer" is no longer the rule. Production now self-checks + submits an outsourced checkpoint too, exactly like an in-house one — just gated on the hand-off actually being received first. Cost/expense entered at that submission is **Production's own** (labor, electricity, etc.) — deliberately a placeholder for now, not the vendor's real cost. The user's own stated plan for that: once Vendor/Purchase gets rebuilt (see the "Multi-unit outsource handoff batching" section above and the Procurement Redesign artifact from the previous day), Purchase will enter the vendor's total cost, shown per-piece in Production, and Production's own final-submit cost covers only their own added labor on top of it — or, for a fully-outsourced item, Purchase enters the whole thing directly. None of that is being built now, by explicit choice.

**Fix**:
- `receiveOutsourceHandoffRound` no longer branches on `qcRequired` or touches any QCJob. When the received step is the checkpoint (found via `qcCheckpointIndex`, not the flag), it now sets `proc.status = 'In Progress'` — unlocking `QcCheckpointPanel` the same way any in-house checkpoint already unlocks (`ProcessExecution.jsx`'s existing `proc.status !== 'Pending'` mount gate, unchanged). A non-checkpoint outsourced step keeps going straight to `'Completed'`, unaffected.
- `markProcessComplete`'s two "auto-advance the next step to `In Progress`" sites (Child Part branch and the generic dynamic-checkpoint branch) now skip a next step whose `type === 'Outsourcing'` — its status stays `'Pending'` until its own hand-off lifecycle (Send → Receive) drives it, which is what keeps the checkpoint panel from mounting too early. Confirmed this doesn't affect the "Send for Outsourcing" button's own unlock check (`canStart`, frontend) — that already reads the *previous* step's status, never this step's own.
- `submitQcCheckpoint`'s hard `proc.type === 'Outsourcing' → 400` refusal replaced with `proc.type === 'Outsourcing' && proc.outsourceStatus !== 'Received' → 400` — submission is allowed once the hand-off is back, refused before that.
- QC-reject already reopens the checkpoint generically, no changes needed: `reopenFinalTestingForRejection` (Sub Child Part/Machine's flat-checklist reject path) and `decideChildPartUnit`'s own reject block both flip the checkpoint back to `'In Progress'` purely by position (`qcCheckpointIndex`/`procs.length-1`), with no type-gating — confirmed by reading both before concluding no fix was needed there.

Verified via `node --check` + import tests on both touched controllers. Not yet re-tested live — next thing to confirm, same order.

## Unit 2+ unreachable when its first step is Outsourcing — found + fixed (2026-09-24, same day)

**Found moving on to Child Part testing** (Fan/CP-001, `welding` Outsourcing as the true first step, orderQuantity 2): clicking "Send for Outsourcing" on Unit 1 never offered Unit 2 in the new batching picker (yesterday's "Multi-unit outsource handoff batching" work, above), even though Unit 2's own tab had been opened in Process Execution. Confirmed against the real order (`extraUnits: []`) that Unit 2 had never actually been materialized server-side at all — not a batching-logic bug, a materialization one, one level down.

**Root cause**: two different lazy-materialization paths exist for `order.extraUnits[]`, and BOTH had gaps for this exact case:
- `productionMfgController.js`'s `getUnitProcesses` DOES lazily materialize on first use — but only ever gets called from `assignTeam`/`startProcess` (and similar), which Production's UI never invokes for an `Outsourcing`-type step at all (that whole branch replaces Start/Assign Team with "Send for Outsourcing" instead). So for a unit whose first reachable step is Outsourcing, this path never fires — there's no "first touch" to trigger it.

## Machine QC checkpoint — per-unit redesign (design agreed 2026-09-24, BUILT 2026-09-24 — not yet live-tested)

**Found live on ORD-0120** (Blower Pulverizer/BP816, `PROD-2026-733365`, qty 2, Process Definition: `assemble` [In-House, QC checkpoint] → `pre painting` → `post painting`). **Root causes, all confirmed by reading the code:**
1. `submitDecision` (`qcController.js`) treats ANY Machine QC approval as final whole-order approval: `setSaleItemStatus(..., 'Approved from QC', { qty: job.quantity })` for the full order quantity, and leaves `QCJob.status = 'Approved'` — the Packaging Queue (`getReadyForPackaging`) lists every `status:'Approved'` Production QCJob with `unitsTotal = job.quantity`. A stock (no-Sale) order would have credited `job.quantity` machines to inventory the same way.
2. Its checkpoint-completion block only handles `checkpointIsLastStep` — a mid-sequence checkpoint is never moved to `'Completed'`, so Unit 1 sits at `'QC Pending'` forever and its next step can never start. (This is the gap flagged-and-deferred earlier today in the "Two more auto-advance-shaped bugs" section — now hit live.)
3. The reject side, `reopenFinalTestingForRejection`, reopens `procs[procs.length - 1]` for EVERY unit — the wrong step for a mid-sequence checkpoint, and units that never even submitted.
4. **Regression found while tracing**: `new-bom-hierarchy-bug-fixes.md` #10's guard (only one unit may be in QC at a time on Machine's shared checklist; refuse a second unit's submission while another is `'QC Pending'`) lived in `saveFinalChecklist` and was NOT carried into Stage 3b's `submitQcCheckpoint` — Unit 2 could currently overwrite Unit 1's in-flight checklist.
5. **The mid-sequence path to dispatch doesn't exist at all today**: when the true last step completes after an earlier checkpoint, `completeFinalProcessStep` → `finalizeMachineOrderCompletion` marks the Sale item `'Production Completed'`, but the packing gate (`ITEM_READY_STATUSES = ['Approved from QC']`) never accepts that — so once bug 1 is fixed, a mid-sequence-checkpoint Machine order could never reach packaging. (It would also have overwritten the premature `'Approved from QC'` from bug 1.)

**Checked on the user's question — the old "does the order have every item" logic:** present and working. `getOrderItemsReadiness` (`storeFlowService.js`) — packing opens only when every Sale item (qty > 0) is `'Approved from QC'`; `setSaleItemStatus` already accumulates `approvedQty` incrementally (`extra.qty`) and only flips an item ready once `approvedQty >= quantity` — exactly the per-unit counting this redesign needs, no change required. Verified on real data: ORD-0093 correctly waits on its unpurchased 2000w generator (3/4). **ORD-0086 / ORD-0047** show "Final Testing: Approved" but "0/1 items" — old July orders created before ProductionOrders carried `saleId`, so their QC approval never found a Sale to update; stuck legacy data, current code doesn't produce this. **Left untouched per the user.** Also confirmed: different machine types in one Sale order are already separate — one ProductionOrder (and one QCJob, keyed `sourceRefId: order.orderId`) per Sale item; they only meet at the Packaging Queue's all-items readiness.

**Agreed design (user's call: "go with child part logic for machine"):**
1. One QCJob per machine line (per ProductionOrder, unchanged), but holding one entry **per unit** (`unitChecks[]`, the Child Part model — decision #4 of "QC placement" above, which was decided for Machine too but only ever built for Child Part). Machine's checklist is single-stage (not Child Part's Initial/Process), so each unit entry carries one checklist. Applies to dynamic-Process-Definition Machine orders; legacy Machine orders on the old `'Final Testing'` step keep their current flow.
2. Production submits each unit's checkpoint independently — units can be in QC at the same time; no shared checklist, so nothing to overwrite and nothing to serialize (supersedes #10's guard for these orders).
3. QC decides each unit separately (like `decideChildPartUnit`): **Reject** → only that unit's checkpoint (by `qcCheckpointIndex`, not the last step) reopens to `'In Progress'` with a rework entry. **Approve** → only that unit's checkpoint → `'Completed'`.
4. **Dispatch/stock rule — corrected by the user** (my first draft wrongly said "QC approval never sends anything to dispatch"; per decisions #2 and #6 above, QC approval IS terminal when the checkpoint is the last step): a unit is done — dispatch-ready if Sale-linked (`setSaleItemStatus(..., 'Approved from QC', { qty: 1 })`), or inventory `+1` if not (the existing Dispatch-vs-Stock fork via `saleId`) — once **both** its checkpoint is QC-approved **and** its true last step is done, triggered by whichever happens last:
   - checkpoint IS the last step → QC's per-unit approval triggers it;
   - checkpoint is mid-sequence → QC's approval only unlocks that unit's next step (normal Assign Team → Start, no auto-advance); completing that unit's true last step (`completeFinalProcessStep`, cost/expense per unit) triggers it, counted as `'Approved from QC'` (QC already passed this unit) — not `'Production Completed'`. Order → `'Completed'` when all units are done.
5. Packaging Queue shows finished units as they arrive ("1 of 2 units ready"), not the whole order quantity at QC approval. **Packing rule unchanged** (confirmed by the user): the whole Sale order still packs together once every item is ready.

## Background / Motivation

Client requirement: rename "Job Work" to two explicit categories — **In House Work** and **Out Source Work** — and extend this concept from Sub Child Part (today, the only level that has it) to **all three BOM levels**: Sub Child Part, Child Part, Machine. Orders must support **hybrid** pipelines (a mix of in-house and outsource steps) with an explicit sequence.

Key decision already made with the client: process steps will be **defined on the BOM itself** (not hardcoded in Production code), and Production/Purchase execution follows whatever pipeline the BOM defines.

The original fuzzy questions that kicked this off (now resolved — see "Custody principle" below):
1. For an outsource step, should it always go straight to Purchase, or should Production receive the order first and request Purchase itself? → Resolved: depends on the step's position in the sequence, not on which BOM level it is.
2. What material should be sent when an order *starts* with an outsource step vs. starts with in-house work, especially for Child Part/Machine where (unlike Sub Child Part) the material need isn't obviously derivable? → Resolved: BOM-level material reference required only for the first step overall; later outsource steps ship whatever Production just produced, plus an optional supplementary list.

## Terminology / gotchas (important — avoid re-confusing these later)

- The client/business meaning of "Sub Child Part" and "Child Part" was **swapped mid-project**, before this discussion. In today's code:
  - `Item.productKind: 'SubChildPart'` = the real, current, **lowest** hierarchy node (one raw material + job work) — this is what `subChildPartDetails` lives on.
  - `Item.productKind: 'ChildPart'` = the **middle** node — was literally named/modeled as `'SubChildPart'` until a 2026-09 rename (old `RDChildPart` / `subChildPartReorderService.js` naming still floating around in places).
  - `Machine` = the top node, references Child Parts via `MachineBOM`.
- There is also a **frozen legacy path** (`RDBOM`, `RDChildPart`, `RDMachine` models/routes) still physically in the codebase but deliberately untouched and no longer reachable from the BOM Management UI (its CRUD routes were removed). It was superseded by the three new parallel documents this whole discussion is about: `Item.subChildPartDetails`, `ChildPartBOM.js`, `MachineBOM.js`. **Do not conflate the legacy RDBOM/RDChildPart/RDMachine models with the current ones** when exploring the codebase for Phase 1/2 work.

## Current architecture (confirmed by code exploration, 2026-09-21)

- `server/models/Inventory.js` — `Item.subChildPartDetails` (lines ~142-197) is the **only** existing outsource/in-house concept in the system: `sourceItem`/`sourceQty`/`sourceUnit`/`sourceDimensionVariantId` (the single raw material and how much one unit consumes), `jobWork: Boolean` (outsource flag), `jobWorkTypes: [String]` (flat, unordered, multi-select — which operations turn the raw material into this part, backed by the `InventoryMasterOption` catalog with `field: 'JobWorkType'`), `jobWorkCost`/`jobWorkCostSource` (`'Manual'|'Actual'`)/`jobWorkCostUpdatedAt`. **No sequence/ordering field exists anywhere today.**
- `server/models/ChildPartBOM.js`, `server/models/MachineBOM.js` — **no** job-work/outsource field exists on either model today (confirmed absent by grep). Both have `materials[]` (`MaterialLineSchema`, defined in `ChildPartBOM.js`, reused by `MachineBOM.js`) as a flat, step-less raw material/tool list — this is the list Phase 1 needs to add step-association to (for OutSource-type internal processes).
- `server/models/ProductionOrder.js` — process steps are hardcoded arrays chosen once at order-creation time based on `orderKind`: `PROCESS_STEPS` (old legacy 6-step Machine pipeline), `SUB_CHILD_PART_STEPS = ['Fabrication','Assembly','Painting']` (today's Child Part pipeline), `MACHINE_BOM_STEPS = ['Assembly','Final Testing']`. `ProcessStepSchema` (lines ~54-77) already has the field shape we'll want to reuse: `{ step, type: enum['Outsourcing','In-House'], status, assignedTeam, startDate/endDate, startedAt/completedAt, qcStatus, qcBy, qcDate, notes, reworks[], subEntries[] }` — `type` exists but is only ever machine-generated from a static map and never gates a real purchase hand-off today.
- `server/models/SubChildPartJobWorkOrder.js` + `server/controllers/subChildPartJobWorkOrderController.js` — a fully **separate** model/flow used only for outsource-only Sub Child Part orders. Auto-created via low-stock sweep (`runSubChildPartOrderSweep`) or cascade from a parent Child Part/Machine order — never manually created by a Purchase user (there is no create route on this router at all). Routing decision at creation is a single boolean check: `isOutSource = !!item.subChildPartDetails.jobWork`. Has a **"rounds" mechanic** (`SubChildPartJobWorkRoundSchema`) — multiple send/receive rounds, each covering a chosen subset of `jobWorkTypes`, with a `materialCase: 'cut'|'whole'` choice and `dimensionVariants[]` selection made by the Purchase user at send time; real stock is deducted once, only on whichever round is sent first; the completing receive requires a real `totalJobWorkCost` (vendor invoice), divided by order quantity and written back to `Item.subChildPartDetails.jobWorkCost`/`jobWorkCostSource:'Actual'`; final receive is QC-gated, stock only credited once QC approves. **No vendor field exists anywhere on the model** (explicit in the model's own comments — "no vendor selection in this first pass").
- Purchase page `pages/accounts/SubChildJobWork.jsx` is read/action-only (Send Round / Receive Round) — no manual order creation, matching the backend.

## Confirmed design decisions

1. **Two-tier process structure per BOM**: **Category** (top-level label, e.g. Fabrication / Assembly / Painting) → **Internal Process** (e.g. Cutting, Bending) nested under it. Each internal process independently carries its own type (`InHouse` / `OutSource`) and sequence number.
2. **Category-level gating**: all internal processes within a category must complete before the next category begins. Sequence exists at both the category level and the internal-process level (nested sequencing).
3. **QC gates**: only at two points — Production's final submit (for an in-house step) and Purchase's final receive (for an outsource round). No additional QC checkpoints are added between every hand-off.
4. **Custody principle** (resolves who initiates an outsource step, uniformly across all three BOM levels):
   - If an outsource step is **first** in the sequence → auto-created the same way it is today (low-stock sweep / cascade from a parent order). No production involvement needed — material is raw stock.
   - If an outsource step comes **after** an in-house step → Production explicitly triggers "send for outsourcing" once its preceding step is complete, since only Production holds the semi-finished intermediate at that point.
5. **One shared order document, not one document per outsource step.**
   - All-outsource order → every step is `OutSource` → behaves exactly like today's Purchase-only flow (Production never sees it).
   - All-in-house order → every step is `InHouse` → behaves exactly like today's Production-only flow (Purchase never sees it).
   - Hybrid order → the **same document**, shared between roles, each with a scoped view: Purchase sees only the outsource steps/rounds relevant to them; Production sees a "waiting for outsource" state while a step is with Purchase, then works their own step(s) in sequence, and explicitly notifies Purchase when the next step needs to go out.
   - Decision (made under development-phase discretion granted by the user, not yet executed): **retire `SubChildPartJobWorkOrder` as a standalone collection**; fold its rounds mechanic into `OutSource`-type steps on a unified `ProductionOrder`.
6. **Materials for OutSource steps**: the BOM-level material tagging is a **reference** into the material list Production/Purchase already build correctly today (sheet-metal → Sheet Metal Plan → area-calculation fallback; length-type/non-sheet-metal → length calculation) — no new quantity-calculation logic is introduced. Required for the very first internal process overall (no prior in-house output exists to send instead); optional/supplementary for later outsource steps (e.g. extra hardware shipped alongside a semi-finished good).
7. **Master Process Template** — two layers:
   - **Catalog layer** (per BOM level: Sub Child Part / Child Part / Machine): a reusable, R&D-maintained list of Category → Internal Process names. Extends today's `JobWorkType` master-options pattern (`InventoryMasterOption`), now hierarchical.
   - **BOM-instance layer**: when building a specific part's BOM, pick which categories apply, then which internal processes under each, then set — specific to that BOM instance — each internal process's type (`InHouse`/`OutSource`) and sequence. The same catalog entry (e.g. "Powder Coating") can be in-house on one BOM and outsourced on another.
   - **UI placement**: the process-definition section is added at the **end of the BOM creation/edit form** (after materials, after cost fields), for all three levels — confirmed by the user, matches where `SubChildPartMasterTab.jsx` currently has its "Job Work" toggle/type-picker section today.
   - **Correction (2026-09-22, after first Phase 1 build)**: catalog management is its own dedicated screen, not inline "+Add" buttons inside the BOM-creation picker. A "Process Templates" button was added — before "New Sub Child Part" / before "New Child Part" / after the machine-select dropdown on the Machine BOM tab — opening `ProcessTemplateManagerDialog.jsx`, a full add/rename/delete screen for that level's Category → Internal Process catalog. `ProcessDefinitionEditor.jsx` (the BOM-creation picker) was correspondingly stripped down to pure selection — it no longer creates new catalog entries itself. Confirmed reasoning: "we will manage a template of process and then select them on bom creation" — BOM creation only ever *picks* from an already-built template; sequence and (for the first/outsource-first step) material selection still happen at BOM-creation time, on the specific BOM instance, exactly as originally designed.
   - **Second correction (2026-09-22, same day)**: two further refinements to the materials picker on an OutSource internal process:
     1. The picker was only offering a BOM's raw `materials[]` — it now also offers the BOM's own assembly-reference lines (a Child Part's `subChildParts[]`, a Machine's `childParts[]`), since either can be what's physically sent to a vendor. Backend validation (`materialLineIds` passed to `validateProcessDefinition`) now checks the union of both id sets.
     2. New per-step field `materialSource: 'ExplicitMaterials' | 'AssembledPart'` on `InternalProcessSchema`. Original assumption ("only the very first step ever needs an explicit material pick, every later step automatically ships whatever the prior step produced") doesn't hold — categories aren't guaranteed to be one continuous chain; two categories can build separate things (e.g. "Frame Fabrication" and "Wiring Prep") that only merge at a later "Assembly" category. So every OutSource step *except* the literal first one (first category, first internal process) now gets an explicit choice: **Assembled part** (ships whatever's been built by the steps before it, no picker) or **Not yet assembled — pick materials** (same combined materials+assembly picker the first step gets). The literal first step is forced to `ExplicitMaterials` server-side in `cleanProcessDefinition`, not just hidden in the UI. Confirmed: this distinction is meaningless for Sub Child Part (only ever one source material) — not built there.
8. **Vendor system**: explicitly deferred, to be worked on standalone after this flow is complete — does not change the process-step design. Future requirement noted for later: vendors will be tagged with categorized services, matched against the same category/internal-process vocabulary used here, so an outsource step can be routed to a capable vendor. Current design is compatible with this without rework.

Splitting into two phases rather than planning/executing everything at once:

## Phase 1 scope decisions (2026-09-21, planning session)

Two decisions made while scoping the Phase 1 plan itself — **do not forget these**, they were made at day-end and not yet reflected in any actual code:

1. **Sub Child Part's old "Job Work" UI and fields are being fully removed, not kept alongside the new design.** No coexistence period, no auto-derivation compatibility layer. The new Process Definition editor (Category → Internal Process, per the confirmed design above) is the only way to define Sub Child Part's process pipeline going forward. This applies to the form UI (`SubChildPartMasterTab.jsx`'s current Job Work toggle + type-picker section) and to the underlying schema fields (`Item.subChildPartDetails.jobWork`, `jobWorkTypes`, and by extension the `/job-work-cost` update endpoint that targets them).
2. **Known, accepted consequence**: `services/subChildPartOrderService.js`'s low-stock sweep (`createSubChildPartOrderForItem`, `isOutSource = !!item.subChildPartDetails.jobWork`) decides outsource-vs-in-house by reading the field being removed. Once Phase 1 ships, this check will no longer work correctly for any Sub Child Part created/edited under the new schema — **the sweep will misroute orders until Phase 2 does the real execution wiring.** User explicitly accepted this for now (system is in dev/staging, not live client usage) rather than have Phase 1 include even a small shim. Proper fix belongs in Phase 2.
3. **New open item this creates, not yet decided**: since the old fields are being removed outright (not just hidden), any *existing* Sub Child Parts that already have `jobWork`/`jobWorkTypes` set will lose that data unless something converts it into the new Category/Internal-Process shape first. Needs a decision next session: does Phase 1 include a one-time conversion script (old data → one auto-generated category with the old `jobWorkTypes` as internal processes, typed per the old `jobWork` boolean), or is this accepted as data loss / deferred? This is now the most time-sensitive open item.

## Phase 1 technical findings (from second exploration pass, 2026-09-21)

Captured so the next session can go straight to writing the plan without re-exploring:

- **No existing hierarchical master-option pattern anywhere in the codebase.** `server/models/InventoryMasterOption.js` (which backs today's `JobWorkType` list) is a flat `{field, value, companyId}` schema, unique on `{companyId, field, value}` — no parent/category field. A new Category→Internal-Process catalog needs a genuinely new model (proposed: `server/models/ProcessCategoryOption.js`, `{companyId, bomLevel: enum['SubChildPart','ChildPart','Machine'], label, internalProcesses: [String]}`, unique on `{companyId, bomLevel, label}` — internal processes as a plain embedded string array to start, no separate collection). Controller pattern to mirror: `inventoryController.js`'s `getInventoryDropdownOptions`/`addInventoryDropdownOption`/`updateInventoryDropdownOption`/`deleteInventoryDropdownOption` (lines 3313–3416), including the delete-guard that blocks removal while anything still references the value.
- **No explicit sequence-number field exists anywhere today** — `ProductionOrder.js`'s step arrays (`PROCESS_STEPS`, `SUB_CHILD_PART_STEPS`, `MACHINE_BOM_STEPS`) and `ProcessStepSchema` all rely on array position, not a stored number. Recommendation carried into planning: keep following that convention (array order = sequence, no separate `sequence` field) for both categories and internal-processes-within-a-category, rather than introducing numeric fields that can drift out of sync with array order.
- **Reordering UI precedent**: `ModernInventoryUI.jsx` has a real, working drag-to-reorder built on `@dnd-kit` (already a project dependency) for a *flat* list (`handleDragEnd` → `arrayMove` → bulk `order` update via `PUT .../items/reorder`). It only handles one flat list, not a nested two-tier structure, so it would need adaptation (or a simpler up/down-arrow-button approach) for reordering categories and, independently, internal processes within each category.
- **Backend CRUD entry points for Phase 1's new field**:
  - Sub Child Part: `controllers/subChildPartMasterController.js` — `createSubChildPart` (~187–238) and `updateSubChildPart` (~245–308, conditional-field-write idiom) in `routes/rdRoutes.js` (`POST/PUT /sub-child-parts...`, ~343–350). New field slots into `Item.subChildPartDetails`.
  - Child Part: `controllers/childPartBOMController.js` — BOM fields (as opposed to base Item fields) go through their own sub-resource endpoints, not the main create/update (see the `production-cost` PUT at `routes/rdRoutes.js` ~372 as the pattern to mirror: add a new `PUT /child-part-master/:id/process-definition`). New field lives on the `ChildPartBOM` model (`models/ChildPartBOM.js`, top-level fields ~87–101), not on `Item`.
  - Machine BOM: `controllers/machineBOMController.js` — **there is no generic "update Machine BOM" route at all**, only `createMachineBOM` plus sub-resource PUTs; mirror the existing `PUT /machine-bom/:machineId/production-cost` pattern with a new `PUT /machine-bom/:machineId/process-definition`, and respect the existing `isLocked` guard used by every other edit action on this BOM.
- **Frontend**: no shared multiselect/picker component exists to reuse across the three tabs — `SubChildPartMasterTab.jsx`'s Job Work Type picker is hand-rolled JSX local to that file. Since the same Category/Internal-Process picker is needed in all three tabs (plus twice in `ChildPartMasterTab.jsx` — once in its create-dialog staged section, once in its live drill-down view), Phase 1 should factor it into one new shared component (e.g. `client/src/components/inventory/ProcessDefinitionEditor.jsx`) rather than duplicating it three times. All three tabs use the same visual idiom for end-of-form additive sections (`border-t border-slate-100 pt-3` + header row with an Add button + list below) — match that for consistency. Insertion points: end of the single dialog in `SubChildPartMasterTab.jsx`; end of the create-dialog staged section and end of the live drill-down Card stack in `ChildPartMasterTab.jsx`; end of the live drill-down Card stack in `MachineBOMTab.jsx` (no create-dialog there to mirror).
