## Open

### B1 🔴 The low-stock cron raises a new PR while received material is still in QC

**What was seen:** after PO-4 (Tool-A) was received, a new auto-reorder PR for Tool-A (PR037)
appeared on the PRs tab, although 25 pieces had just arrived and were waiting for QC.

**Why it happens (verified in the code; not yet confirmed against the data, see "To confirm"):**
- `jobs/lowStockReorderCron.js` runs every 30 minutes. Per item it raises a request when **free
  stock ≤ minimum stock**, unless an **auto-generated** request for that item is already open.
- "Open" is `OPEN_STATUSES = ['Pending', 'Approved', 'Ordered']` (line 21). The same list is used
  for fabrication sizes (`checkFabricationVariants`).
- Store's receive sets the request to **`Received`**, which is not in the list, so the guard
  stops. But **stock only goes up when QC passes** (`qcController.submitDecision`), so for as long
  as the delivery waits for QC, free stock still looks low and the next sweep raises a duplicate.
- **Second gap:** after QC rejects part of a delivery and the vendor says **"Will replace"**, the
  replacement request is not an auto request (`replacementFor`, not `autoGenerated`), so it doesn't
  block the cron either. If the pieces that passed leave stock at or under the minimum, another
  auto PR is raised while a replacement is already on the way.
- **Third gap:** the guard looks only at **auto** requests. Manual PRs, or an open PO that already
  covers the item, don't count either.
- This is the still-open **R1** in `procurement-workflow-2026-10.md` (reorder trigger =
  free stock **+ confirmed incoming** ≤ reorder level). The workflow doc (§6.2) assumes the engine
  counts incoming; this cron doesn't.

**Not a bug:** a new request after the vendor **refunds, gives credit or refuses** is correct,
because the material really is missing.

**Proposed fix, decision needed (the user wanted to talk about it first):**
- **Option A (small, recommended):** keep the guard, but treat an auto request as still open until
  its delivery is decided.
  - `Received` counts as open while any of its purchase QC jobs is still Pending / In Progress
    (`QCJob.purchaseRequestId`, `source: 'Purchase'`).
  - Also skip while a rejection for the item has the answer "Will replace" and its replacement
    hasn't passed QC (`PurchaseRejection.outcome`, `status`).
- **Option B (blueprint formula):** skip when
  `free stock + open-PO incoming + QC-pending quantity > minimum`. It reuses
  `stockContextService.incomingFromPurchases` and is more correct, but it touches more code, and
  per size for fabrication.
- Either way: tests for plain and fabrication items, a QC-pending case, a replacement case, and a
  refund case (should still raise).

**To confirm (needs the database):** PR037's `createdAt` against the Tool-A QC jobs' creation and
decision times. If PR037 was created **after** the receive and **before** the QC pass, that's B1.
```
db.purchaserequests.find({ requestId: 'PR037' }, { requestId: 1, status: 1, autoGenerated: 1, createdAt: 1, requestDate: 1 })
db.qcjobs.find({ itemName: 'Tool-A', source: 'Purchase' }, { qcJobId: 1, status: 1, createdAt: 1, updatedAt: 1 })
```

### B2c 🟡 Refunds & credits (Vendor Payment) has no pagination or "open only" view
Found 2026-10-15 while testing slice 6 (2e / 2f).
- The list is per selected vendor. The server returns the newest 200 (`listMoneyBack`:
  `.sort({ createdAt: -1 }).limit(200)`), and the page shows only the **first 30**
  (`VendorMoneyBackList.jsx`: `items.slice(0, 30)`), with no "show more" and no status filter,
  although the server already accepts `?status=`.
- Refunded / Used / Written off rows stay forever, so the list only grows. With many rows, an old
  open item (a **Refund due** or **Credit available**) can fall out of the newest 30 and become
  invisible, while the "N open" count still includes it (up to the 200 fetched).
- Fix idea: open items always on top; the history behind a "Show history" toggle with pagination;
  optional status chips (Open / All). Server side: page the list and count open items separately.

### B3 🟡 Old single-request PO edit still sets one quantity on every request
`purchaseController.updatePurchase` (the old PO-edit route) still gives every request on a line the
same quantity (the §40 bug, in the old route). v2 never edits a PO and no page calls it, so it can't
fire today. Fix when that backend is cleaned up: remove the route, or use `splitLineQuantity`.

### B4 🟡 The legacy RFQ "select winner" path still creates POs the old way
Noted in §5: it skips the approval threshold and the new rules. No screen reaches it since the RFQ
pages were retired. Remove when the old RFQ backend is cleaned up.
