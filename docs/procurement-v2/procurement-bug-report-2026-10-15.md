## Open

### B1 🔴 The low-stock cron raises a new PR while received material is still in QC

**What was seen:** after PO-4 (Tool-A) was received, a new auto-reorder PR for Tool-A (PR037)
appeared on the PRs tab, although 25 pieces had just arrived and were waiting for QC.

**Why it happens (verified in the code; not yet confirmed against the data, see "To confirm"):**
- `jobs/lowStockReorderCron.js` runs every 30 minutes. Per item it raises a request when **free
  stock ≤ minimum stock**, unless an **auto-generated** request for that item is already open.
- "Open" is `OPEN_STATUSES = ['Pending', 'Approved', 'Ordered']` (line 21). The same list is used
  for fabrication sizes (`checkFabricationVariants`).
- Store's receive sets the request to **`Received`**, which is not in the list, so the guard
  stops. But **stock only goes up when QC passes** (`qcController.submitDecision`), so for as long
  as the delivery waits for QC, free stock still looks low and the next sweep raises a duplicate.
- **Second gap:** after QC rejects part of a delivery and the vendor says **"Will replace"**, the
  replacement request is not an auto request (`replacementFor`, not `autoGenerated`), so it doesn't
  block the cron either. If the pieces that passed leave stock at or under the minimum, another
  auto PR is raised while a replacement is already on the way.
- **Third gap:** the guard looks only at **auto** requests. Manual PRs, or an open PO that already
  covers the item, don't count either.
- This is the still-open **R1** in `procurement-workflow-2026-10.md` (reorder trigger =
  free stock **+ confirmed incoming** ≤ reorder level). The workflow doc (§6.2) assumes the engine
  counts incoming; this cron doesn't.

**Not a bug:** a new request after the vendor **refunds, gives credit or refuses** is correct,
because the material really is missing.

**Proposed fix, decision needed (the user wanted to talk about it first):**
- **Option A (small, recommended):** keep the guard, but treat an auto request as still open until
  its delivery is decided.
  - `Received` counts as open while any of its purchase QC jobs is still Pending / In Progress
    (`QCJob.purchaseRequestId`, `source: 'Purchase'`).
  - Also skip while a rejection for the item has the answer "Will replace" and its replacement
    hasn't passed QC (`PurchaseRejection.outcome`, `status`).
- **Option B (blueprint formula):** skip when
  `free stock + open-PO incoming + QC-pending quantity > minimum`. It reuses
  `stockContextService.incomingFromPurchases` and is more correct, but it touches more code, and
  per size for fabrication.
- Either way: tests for plain and fabrication items, a QC-pending case, a replacement case, and a
  refund case (should still raise).

**To confirm (needs the database):** PR037's `createdAt` against the Tool-A QC jobs' creation and
decision times. If PR037 was created **after** the receive and **before** the QC pass, that's B1.
```
db.purchaserequests.find({ requestId: 'PR037' }, { requestId: 1, status: 1, autoGenerated: 1, createdAt: 1, requestDate: 1 })
db.qcjobs.find({ itemName: 'Tool-A', source: 'Purchase' }, { qcJobId: 1, status: 1, createdAt: 1, updatedAt: 1 })
```

### B2c 🟡 Refunds & credits (Vendor Payment) has no pagination or "open only" view
Found 2026-10-15 while testing slice 6 (2e / 2f).
- The list is per selected vendor. The server returns the newest 200 (`listMoneyBack`:
  `.sort({ createdAt: -1 }).limit(200)`), and the page shows only the **first 30**
  (`VendorMoneyBackList.jsx`: `items.slice(0, 30)`), with no "show more" and no status filter,
  although the server already accepts `?status=`.
- Refunded / Used / Written off rows stay forever, so the list only grows. With many rows, an old
  open item (a **Refund due** or **Credit available**) can fall out of the newest 30 and become
  invisible, while the "N open" count still includes it (up to the 200 fetched).
- Fix idea: open items always on top; the history behind a "Show history" toggle with pagination;
  optional status chips (Open / All). Server side: page the list and count open items separately.

### B5 🟡 Serial numbers that differ only by a hyphen count as different serials (decision needed)
Found 2026-10-16 while testing slice 6 (3b, 3e).
- The Bairing serials were received as `BRG0101` … `BRG0105` (no hyphen). The replacement was then
  received as **`BRG-0102`** (I expected it to be refused as already received). It was **accepted**, so Serial Numbers
  now holds both `BRG0102` and `BRG-0102`.
- Cause: `serialKeyOf` (`services/purchasedUnitService.js`) compares `trim().toUpperCase()` only, so
  punctuation counts. The unique index on the key therefore treats the two as different.
- Same effect on a warranty claim: typing `BRG-0103` for the stored `BRG0103` finds nothing and the
  claim form falls back to "Not in our serial records".
- **Decision needed:**
  - **Yes, ignore hyphens / spaces / dots in the key** (e.g. strip `[\s\-._/]`): stops this kind of
    duplicate, and a customer quoting `BRG-0103` still finds `BRG0103`. Risk: two real serials from
    a vendor that differ only by punctuation would collide. The key is stored, so existing rows
    need their keys rebuilt.
  - **No, leave as is:** serials stay exactly as the vendor wrote them, and Store and Complaints must
    type them the same way.
- Test data: the extra `BRG-0102` row is the replacement of `BRG0101` (REJ-0003, Replaced).

### B6 🟡 Vendor Warranty score differs between the list and the expanded vendor panel (OPEN INVESTIGATION, unconfirmed)
Found 2026-10-16 while testing slice 6 section 4 (sujeet, Vendor Ratings).

**Status:** not confirmed. It can't be checked in the browser: Purchase → RFQ/PO → All quotes shows
rate, GST, quantity and delivery for each quote, but **not warranty months**, and it lists only what
can be bought now. To investigate with database access (e.g. a local session):
```
// sujeet's quotes that carry a warranty (the list counts these; the panel only counts items on his POs)
db.vendorbids.find({ vendor: ObjectId('<sujeet _id>'), warrantyMonths: { $gt: 0 } },
  { group: 1, productName: 1, warrantyMonths: 1, status: 1, submittedAt: 1 })
```
If this returns quotes on items that are not on sujeet's POs (e.g. Bairing, which went to mahesh),
the theory below is right. If it returns nothing, the 100 comes from somewhere else and the
reading below is wrong.

- The list bars and the Watchlist card show **Warranty 100** for sujeet (his score is 91 only with
  it counted: (93×25 + 76×30 + 100×20 + 100×10 + 100×10) ÷ 95 = 90.6). The expanded panel under the
  same vendor shows Warranty "—" and "No warranty quoted and no claims".
- Cause (read in the code, not yet confirmed against the data): `computeVendorScores` takes the
  item list for the warranty comparison from the **POs of the vendors asked for**
  (`vendorScoreService.js`, the `itemIds` taken from `pos`). The list asks for every vendor, so
  sujeet's quotes on items that went to other vendors (e.g. ss sheet) are included. The panel asks
  for sujeet alone (`withEvidence`), so only Tool-A is looked at, which has no warranty quoted.
  The two calls therefore use different item sets for the same vendor.
- Effect: a vendor's score can change depending on which screen asks for it.
- Fix idea: take the items for the warranty comparison from the vendor's own quotes (their bids),
  not from the POs of whoever is in the query; then add a test that the score is the same for one
  vendor alone and for all vendors together.

### B8 🟡 Ledger page: Total Debit / Total Credit / Closing Balance are for the current page only
Found 2026-10-16 (slice 6, section 5, Ledger). Not from the purchase work: the page has done this
since the first commit.
- `LedgerRecord.jsx` adds up `records`, which holds only the 15 rows of the page on screen
  (`limit: 15`), so the tiles are page totals, not totals for the chosen dates.
- Seen: after one new debit of ₹33,040 was posted, Total Debit rose by exactly ₹33,040 but Total
  Credit **fell by ₹10,000**, because one ₹10,000 credit row moved from page 1 to page 2.
- Closing Balance is `records[0].balance`, so on page 2 it shows that page's newest balance, not the
  account's closing balance.
- Fix: have the server return the period totals and the real closing balance with the page of rows.

### B10 🟡 Company Admin dashboard: "Purchase value" and "Top 3 vendors" count the original PO totals (decision needed)
Found 2026-10-16 (slice 6, section 5, dashboards).
- Purchase value reads **₹1,62,520** (4 POs), the same as on 14 Oct, although since then PO-1 was
  cancelled after its advance (₹26,862.60 moved to money-back), PO-2 was short closed (₹8,896.86 →
  ₹8,102.78), PO-3b's generator was refunded (bill ₹30,655 → ₹2,655) and PO-4 lost ₹860 to a QC
  refusal.
- The vendor shares match the **original** totals exactly: rahul 73.8% (₹1,19,914.88), mahesh 18.9%
  (₹30,655), sujeet 7.4% (₹11,950).
- Cause: `purchaseDashboardService.js` sums `po.grandTotal` (what was ordered). The PO's **bill**
  (`PurchaseInvoice.totalAmount`) is the figure that follows cancellations, short closes and QC
  refusals.
- **Decision needed:** is management meant to see what was **ordered** (as now, and as the design doc
  says: "Σ PO totals") or what we **ended up buying** (the bill)? If the second, switch the sum to the
  bill total and keep the trend and top-3 share on the same figure.
